1. EXECUTIVE SUMMARY
================================================================================

Junkcoin (JKC) is an AuxPow (Auxiliary Proof-of-Work) cryptocurrency that
merged mines with Bitcoin. This document describes a novel architecture where
Junkcoin serves as a settlement layer for all UTXO-based AuxPow chains.

Key innovations:
- UTXO-VM: Deterministic WebAssembly execution on UTXO chains
- Single-Use Seals: Cryptographic state transitions
- Cross-Chain Anchoring: State commitment via OP_RETURN envelopes
- Privacy: Stealth settlement for confidential transfers

================================================================================
2. PROBLEM STATEMENT
================================================================================

2.1 Current AuxPow Landscape
--------------------------------------------------------------------------------

AuxPow chains (Junkcoin, Dogecoin, Litecoin forks) merged mine with
Bitcoin/Litecoin for security. However, they lack:

- State transition layer: No smart contracts or state management
- Cross-chain communication: No standard protocol for inter-chain transfers
- Settlement finality: No cryptographic proof of state across chains

2.2 Limitations of Existing Solutions
--------------------------------------------------------------------------------

| Solution          | Limitation                                    |
|-------------------|-----------------------------------------------|
| Bitcoin Sidechains | Requires federated peg, not trustless        |
| Atomic Swaps       | Limited to asset transfers, no state         |
| Bridge Contracts   | Centralized, single point of failure         |

2.3 The Junkcoin Opportunity
--------------------------------------------------------------------------------

Junkcoin has:
- Bitcoin-grade security via AuxPow
- Low transaction fees
- Active development community
- Existing infrastructure (exchanges, wallets)

4. TECHNICAL COMPONENTS
================================================================================

4.1 UTXO-VM Runtime
--------------------------------------------------------------------------------

The UTXO-VM runtime executes WebAssembly contracts deterministically:

- Engine: Wasmtime 18.0.2
- Gas Model: Fuel-based metering
- Memory: Bounded (32 pages max)
- State: Seal-based, not account-based

Host Functions:
  host_get_caller()     → Get transaction signer
  host_get_satoshis()   → Get locked amount
  host_get_seal()       → Get current UTXO seal
  host_emit_event()     → Emit indexable event
  host_create_object()  → Spawn child object
  host_stealth_settle() → Privacy settlement

4.2 Single-Use Seals
--------------------------------------------------------------------------------

A seal is a reference to a specific UTXO:

  Seal = txid:vout

Properties:
- Unique: Each UTXO can only be spent once
- Cryptographic: Bound to transaction signature
- Verifiable: Anyone can verify UTXO existence

State Transition:
  S_t → S_{t+1}

  1. Consume input seal (spend UTXO)
  2. Execute contract logic
  3. Create output seal (new UTXO)
  4. Update state data

4.3 Envelope Protocol
--------------------------------------------------------------------------------

Format:
  OP_FALSE OP_IF
    OP_PUSH "utxovm"           // Protocol identifier
    OP_PUSH 0x01               // Version
    OP_PUSH <content_type>     // MIME type
    OP_PUSH <payload>          // Data
  OP_ENDIF

Content Types:
  application/wasm    → Contract deployment
  application/json    → Method calls, state updates

4.4 Cross-Chain Envelope
--------------------------------------------------------------------------------

State Anchor (Child Chain → Junkcoin):
  {
    "type": "state_anchor",
    "chainId": "chain_a_testnet",
    "merkleRoot": "0xabc123...",
    "blockHeight": 12345,
    "blockHash": "0xdef456...",
    "stateRoot": "0x789abc...",
    "prevSeal": "txid:vout"
  }

State Claim (Junkcoin → Child Chain):
  {
    "type": "state_claim",
    "chainId": "chain_a_testnet",
    "junkcoinSeal": "txid:vout",
    "merkleRoot": "0xabc123...",
    "proof": ["0x...", "0x..."],
    "signatures": ["0x..."]
  }

5. CROSS-CHAIN PROTOCOL
================================================================================

5.1 State Anchoring Flow
--------------------------------------------------------------------------------

Step 1: Child Chain A computes state root
  - Collect all transactions in block
  - Build Merkle tree
  - Compute state root hash

Step 2: A broadcasts anchor to Junkcoin
  - Create OP_RETURN with state_anchor payload
  - Include merkleRoot, blockHeight, blockHash
  - Reference previous seal (chain continuity)

Step 3: Junkcoin indexer stores anchor
  - Parse envelope
  - Create smart object with seal
  - Store state data

Step 4: A receives seal confirmation
  - Seal = txid:vout from Junkcoin
  - Can now reference this seal in future operations

5.2 State Claim Verification
--------------------------------------------------------------------------------

Child Chain B receives state claim from A:

Step 1: B queries Junkcoin for seal
  - GET /api/v1/object/{seal}
  - Verify seal exists and is unspent

Step 2: B verifies merkle proof
  - Reconstruct merkle root from proof
  - Compare with stored merkleRoot

Step 3: B accepts state
  - Update local state
  - Create confirmation transaction

5.3 Cross-Chain Transfer Flow
--------------------------------------------------------------------------------

Alice (Chain A) wants to send tokens to Bob (Chain B):

Step 1: Alice locks tokens on Chain A
  - Create seal on Chain A
  - Include transfer details in state

Step 2: Relayer broadcasts to Junkcoin
  - Create cross_chain_transfer envelope
  - Include source seal, destination info

Step 3: Bob claims on Chain B
  - Provide proof of Junkcoin seal
  - Bob's address receives tokens

Step 4: Settlement complete
  - Chain A seal consumed
  - Chain B seal created
  - Junkcoin has audit trail

6. VERIFICATION MECHANISM
================================================================================

6.1 Seal Verification
--------------------------------------------------------------------------------

To verify a seal exists on Junkcoin:

  GET /api/v1/object/{objectId}

Response:
  {
    "objectId": "obj_abc123",
    "seal": "txid:vout",
    "stateData": { ... },
    "owner": "0x..."
  }

Verification:
  1. Check seal matches expected txid:vout
  2. Verify stateData contains expected merkleRoot
  3. Confirm seal is unspent (latest state)

6.2 Merkle Proof Verification
--------------------------------------------------------------------------------

Given:
  - Leaf hash (transaction hash)
  - Proof path (sibling hashes)
  - Root hash (stored on Junkcoin)

Verification:
  1. Start with leaf hash
  2. For each proof element:
     - Concatenate with current hash
     - Compute SHA256
  3. Compare final hash with root

6.3 State Consistency Check
--------------------------------------------------------------------------------

To ensure cross-chain consistency:

  1. Junkcoin stores state anchors from multiple chains
  2. Each anchor includes block height and hash
  3. Chains can verify:
     - Their anchor exists on Junkcoin
     - No conflicting anchors for same block
     - Anchor chain is unbroken

7. SECURITY MODEL
================================================================================

7.1 Threat Model
--------------------------------------------------------------------------------

Attacker capabilities:
  - Can create transactions on any chain
  - Can broadcast to multiple chains simultaneously
  - Cannot break cryptographic primitives

Defenses:
  - Seals are UTXOs (double-spend prevention)
  - Merkle proofs are deterministic
  - Signatures are cryptographic

7.2 Trust Assumptions
--------------------------------------------------------------------------------

- Junkcoin miners are honest majority
- At least one honest relayer exists
- Cryptographic primitives are secure

7.3 Finality
--------------------------------------------------------------------------------

Probabilistic finality:
  - 1 confirmation: ~99% final
  - 6 confirmations: ~99.99% final
  - 60 confirmations: ~99.999999% final

Child chains should wait for N confirmations before accepting state.

12.3 Merkle Proof Verification
--------------------------------------------------------------------------------

```javascript
function verifyMerkleProof(leaf, proof, root) {
  let current = leaf;
  
  for (const sibling of proof) {
    const combined = Buffer.concat([current, sibling]);
    current = sha256(combined);
  }
  
  return current.equals(root);
}
```

12.4 Cross-Chain Transfer
--------------------------------------------------------------------------------

```javascript
// Step 1: Lock tokens on source chain
const lockTx = await sourceChain.lock({
  amount: 10000,
  receiver: bobAddress,
  destChain: "chain_b"
});

// Step 2: Create anchor on Junkcoin
const anchor = await junkcoin.anchor({
  sourceChain: "chain_a",
  lockTxid: lockTx.txid,
  receiver: bobAddress
});

// Step 3: Claim on destination chain
const claimTx = await destinationChain.claim({
  anchorSeal: anchor.seal,
  proof: anchor.merkleProof,
  receiver: bobAddress
});
```
